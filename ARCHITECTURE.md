## Описание проекта

**Цель**: разработать backend-ориентированное dating-приложение с многоуровневой системой рейтинга анкет и современной, масштабируемой архитектурой.

Приложение должно:
- **Формировать рейтинг анкет** на основе анкетных данных и поведения пользователей.
- **Обрабатывать события взаимодействия** (лайки, скипы, мэтчи, диалоги) в потоковом режиме.
- **Обеспечивать высокую производительность** за счёт кэширования, отложенных пересчётов и очередей сообщений.

Проект предполагается как набор микросервисов (или модульных bounded context’ов) с чёткими зонами ответственности.

---

## Сервисы и их ответственность

- **Auth / Users Service**
  - Регистрация и аутентификация пользователей.
  - Хранение основных данных пользователя (email/телефон, пароль, базовые настройки).
  - Управление сессиями/токенами доступа (JWT или аналог).

- **Profile Service (Анкеты)**
  - Хранение расширенной информации анкеты:
    - возраст, пол, город, геолокация;
    - интересы (теги/категории);
    - описание, предпочтения (кого ищет, возрастной диапазон, пол, радиус, город).
  - Управление фотографиями анкет (метаданные + ссылки на S3/Minio).
  - Оценка **полноты заполнения профиля** и количества фотографий (базовый вклад в первичный рейтинг).

- **Rating Service (Рейтинги)**
  - Реализация **трёхуровневой модели рейтинга**:
    - Уровень 1: первичный рейтинг.
    - Уровень 2: поведенческий рейтинг (динамический).
    - Уровень 3: комбинированный рейтинг.
  - Хранение агрегированных рейтингов в отдельной таблице/схеме БД.
  - Регулярные пересчёты рейтингов по расписанию через **Celery**.
  - Интеграция с очередями сообщений (Kafka/RabbitMQ) для обработки событий взаимодействия.

- **Interaction Service (Взаимодействия / Лайки / Матчи)**
  - Обработка действий:
    - лайк анкеты;
    - пропуск анкеты;
    - отмена лайка (если предусмотрено);
    - фиксация факта мэтча (взаимный лайк).
  - Генерация событий в MQ (например, `profile_liked`, `profile_skipped`, `match_created`), которые дальше обрабатываются сервисом рейтингов.
  - Ведение статистики лайков/скипов/мэтчей для расчёта поведенческого рейтинга.

- **Dialog / Chat Service (Диалоги)**
  - Создание диалогов после мэтча.
  - Отправка и хранение сообщений (минимально — текст, в перспективе — вложения).
  - Генерация событий в MQ (`dialog_started`, `message_sent`) для учёта в поведенческом рейтинге.

- **Feed / Recommendation Service (Лента анкет)**
  - Формирование списка анкет для показа пользователю:
    - с учётом преднастроенных фильтров (пол, возраст, город/радиус);
    - с учётом комбинированного рейтинга.
  - Интеграция с **Redis**:
    - предварительное формирование и кэширование отсортированных списков анкет;
    - при старте сессии пользователю:
      - первая анкета рассчитывается «вживую» через все слои сервисов;
      - параллельно в Redis подгружается пачка следующих N (например, 10) анкет;
      - по мере «выработки» пачки происходит фоновая догрузка следующей.

- **Media Service (Хранение изображений)**
  - Загрузка и управление изображениями анкет.
  - Интеграция с **S3-совместимым хранилищем (Minio)**:
    - генерация presigned URL для загрузки/просмотра;
    - хранение только ссылок и метаданных в основной БД.

- **Metrics / Logging / Monitoring**
  - Сбор технических и бизнес-метрик:
    - количество лайков/скипов/мэтчей;
    - время ответа ключевых эндпоинтов;
    - количество активных пользователей в интервалах времени;
    - статистика по пересчётам рейтингов (успешные/ошибки, длительность задач Celery).
  - Централизованное логирование запросов и фоновых задач.

## Архитектура и взаимодействие компонентов

### Общий обзор

- **Клиенты** (мобильное приложение / веб-клиент) обращаются к **API Gateway** или общему Backend API.
- Backend разбит на несколько доменных сервисов (описаны выше).
- Для обмена событиями между сервисами используется **сообщения в MQ** (Kafka/RabbitMQ/другая MQ).
- Асинхронные и периодические задачи выполняются через **Celery** (worker’ы).
- **Redis** используется как быстрый кэш для:
  - предварительно отсортированных списков анкет;
  - сессий/токенов (опционально);
  - временных данных (rate limiting и т.п.).
- **S3/Minio** для файлов (изображения анкет).
- Основная **реляционная БД** (PostgreSQL или аналог) для транзакционных данных.

### Поток взаимодействия (упрощённо)

1. **Регистрация/авторизация**:
   - Пользователь создаёт аккаунт в `Auth Service`.
   - После регистрации создаётся базовая запись профиля в `Profile Service`.

2. **Заполнение анкеты**:
   - Пользователь заполняет анкету, загружает фото (через `Media Service` → S3/Minio).
   - `Profile Service` сохраняет данные и рассчитывает степень заполненности профиля.
   - `Rating Service` формирует **первичный рейтинг (Уровень 1)** на основе:
     - возраста, пола, города, интересов;
     - соответствия настройкам поиска (если есть default-преференции);
     - полноты анкеты и количества фото.

3. **Формирование ленты анкет**:
   - Пользователь открывает экран со свайпами/анкетами.
   - `Feed Service` запрашивает текущий кэш в **Redis**:
     - если кэш пуст или устарел, запрашивает `Rating Service`/`Profile Service` для генерации свежего списка, сохраняет его в Redis.
     - первая анкета может вычисляться полностью онлайн, параллельно в Redis подгружается пачка следующих N анкет.

4. **Лайки/скипы/мэтчи**:
   - Пользователь лайкает или скипает анкету через `Interaction Service`.
   - `Interaction Service`:
     - записывает событие в БД (для аналитики и истории);
     - публикует событие в MQ (`profile_liked`, `profile_skipped`).
   - При взаимном лайке создаётся мэтч (`match_created`), и возможно инициируется диалог в `Dialog Service`.

5. **Диалоги**:
   - При появлении мэтча `Dialog Service` создаёт сущность диалога.
   - При первых сообщениях генерируются события (`dialog_started`, `message_sent`), которые также попадают в MQ.

6. **Обновление поведенческого рейтинга (Уровень 2)**:
   - `Rating Service` подписан на события MQ.
   - На основе:
     - количества лайков и их отношения к скипам;
     - частоты взаимных лайков (мэтчей);
     - количества начатых диалогов после мэтча;
     - временных паттернов активности (в какие часы происходят лайки/ответы);
   - рассчитывается **поведенческий рейтинг**. Для тяжёлых перерасчётов используются задачи Celery.

7. **Комбинированный рейтинг (Уровень 3)**:
   - В отдельной задаче (через Celery по расписанию) `Rating Service`:
     - интегрирует **первичный** и **поведенческий** рейтинги по весовой модели;
     - учитывает дополнительные факторы (например, **реферальная активность — приглашение друзей**).
   - Результат записывается в отдельную таблицу рейтингов.
   - Кэш Redis обновляется (либо по событию, либо по TTL).

## Схема данных (черновой вариант)

Ниже — логическая модель основных сущностей (без конкретного синтаксиса SQL).

- **Пользователь и профиль**
  - `users`
    - `id`
    - `email` / `phone`
    - `password_hash`
    - `created_at`
    - `status` (active, banned, deleted и т.п.)
  - `profiles`
    - `id`
    - `user_id` (FK → `users.id`)
    - `gender`
    - `birth_date`
    - `city`
    - `location_lat`, `location_lon` (опционально)
    - `bio`
    - `profile_completeness_score` (0–1 или 0–100)
    - `photos_count`
    - `created_at`, `updated_at`
  - `profile_interests`
    - `id`
    - `profile_id` (FK)
    - `interest_tag` (строка или FK в отдельную таблицу `interests`)
  - `profile_preferences`
    - `id`
    - `profile_id` (FK)
    - `preferred_gender`
    - `age_min`, `age_max`
    - `city` или `radius_km`

- **Фото**
  - `profile_photos`
    - `id`
    - `profile_id` (FK)
    - `storage_key` (путь/ключ в S3/Minio)
    - `url` (опционально, если используется CDN/presigned)
    - `is_main` (флаг основной фотографии)
    - `order_index`
    - `created_at`

- **Взаимодействия и мэтчи**
  - `profile_likes`
    - `id`
    - `from_profile_id`
    - `to_profile_id`
    - `is_like` (true = лайк, false = скип, либо отдельная таблица `skips`)
    - `created_at`
  - `matches`
    - `id`
    - `profile_id_1`
    - `profile_id_2`
    - `created_at`
    - `status` (active, blocked, closed)

- **Диалоги**
  - `dialogs`
    - `id`
    - `match_id` (FK → `matches.id`)
    - `created_at`
  - `messages`
    - `id`
    - `dialog_id` (FK)
    - `from_profile_id`
    - `text`
    - `created_at`
    - `is_read`

- **Рейтинги**
  - `profile_ratings`
    - `id`
    - `profile_id` (FK)
    - `primary_rating` (Уровень 1)
    - `behavior_rating` (Уровень 2)
    - `combined_rating` (Уровень 3)
    - `likes_count`
    - `skips_count`
    - `matches_count`
    - `dialogs_after_match_count`
    - `referral_score` (баллы за приглашённых друзей)
    - `last_recalculated_at`

- **Рефералы**
  - `referrals`
    - `id`
    - `inviter_profile_id`
    - `invited_user_id`
    - `status` (registered, active, bonus_applied)
    - `created_at`

- **Технические таблицы (примерно)**
  - `rating_recalc_jobs` — история задач пересчёта рейтингов.
  - `events_log` — лог бизнес-событий (если нужно для аналитики отдельно от MQ).

## Рейтинг: уровни и алгоритмы (концептуально)

- **Уровень 1 — Первичный рейтинг**
  - Основывается на:
    - пол, возраст, город, интересы;
    - полнота заполнения профиля (`profile_completeness_score`);
    - количество и качество (наличие главной, минимум N) фотографий.
  - Учитывает **первичные предпочтения пользователя**:
    - возрастной диапазон партнёров;
    - пол и город/радиус.
  - Может быть реализован как взвешенная сумма нормализованных факторов.

- **Уровень 2 — Поведенческий рейтинг**
  - Динамически корректируется на основе поведения других пользователей:
    - общее количество лайков анкеты;
    - соотношение лайков и пропусков;
    - частота взаимных лайков (мэтчей);
    - частота начала диалогов после мэтча;
    - временные параметры (например, «анкета часто лайкается в прайм-тайм»).
  - Все события поступают через MQ, обрабатываются worker’ами Celery и агрегируются в `profile_ratings`.

- **Уровень 3 — Комбинированный рейтинг**
  - Интеграция первичного и поведенческого рейтингов **по весовой модели**:
    - `combined_rating = w1 * primary_rating + w2 * behavior_rating + w3 * referral_score + ...`
  - Учитывает дополнительные факторы:
    - участие в реферальной программе (приглашение друзей);
    - возможно, дополнительные бонусы за активность.
  - Пересчёт по расписанию (например, каждые N минут/часов) через Celery.

## Использование Celery, Redis, MQ и S3 (Minio)

- **Celery**
  - Периодические задачи:
    - массовый пересчёт поведенческого и комбинированного рейтингов;
    - очистка устаревших данных в Redis;
    - агрегация статистики (метрики).
  - Фоновые задачи:
    - пересчёт рейтинга конкретной анкеты после всплеска активности;
    - обработка тяжёлых запросов/логики.

- **Redis**
  - Кэш предранжированных списков анкет по пользователям/сегментам.
  - Пример:
    - при входе пользователя формируется/обновляется список анкет;
    - первая анкета — онлайн расчёт, параллельно в Redis складывается список из N следующих;
    - при достижении конца пачки — асинхронно формируется следующая.

- **Apache Kafka / RabbitMQ / MQ**
  - Потоковая обработка событий:
    - `profile_liked`, `profile_skipped`, `match_created`, `dialog_started`, `message_sent`, `referral_registered` и др.
  - Декуплинг: сервисы лайков, диалогов, рейтингов и аналитики работают независимо, подписываясь на нужные топики/очереди.

- **S3 / Minio**
  - Хранение фотографий:
    - загрузка через presigned URL;
    - проверка/валидация файлов (тип, размер);
    - возможность лёгкой замены Minio на облачное S3.
